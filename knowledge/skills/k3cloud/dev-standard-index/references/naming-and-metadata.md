# 业务对象开发规范:命名 + 元数据设计 🟡

> 命名任何自定义元素之前必读。命名不规范 = 多安装包冲突 + 质量门禁扣分 + 后期改不起(标识写进元数据就固化了)。

---

## 1. 命名规范

| 元素 | 规则 | 示例 |
|---|---|---|
| 业务对象 Key | 默认用系统生成的 GUID;要自定义则**必须以开发商代码加下划线排头**,长度 ≤30 字符,只能字母 + 下划线 | `PAAB_xxxxx` |
| 扩展字段的**标识和属性** | 必须以开发商代码加下划线排头 | `PAAB_xxxxx` |
| 扩展字段的**物理字段名** | 必须包含开发商代码 | `F_PAAB_xxxxx` |
| 任意扩展控件(标签 / 页签 / 面板等) | 标识必须以开发商代码加下划线排头 | `PAAB_LabelXXX`、`PAAB_TabXXX` |

开发商代码 = 你在金蝶协同开发平台注册的 ISV 代码(如 `PAAB` / `ABC`),也是 DLL 命名空间首段和自定义表名前缀(`ABC_T_USER`)的同一来源——**同一个项目里这四处的前缀必须一致**。

**agent 行为约定**:给用户生成字段 / 控件时,主动用项目 devCode + 前缀命名,并在话术里说明"按金蝶二开规范,标识带开发商代码前缀"。OpenDeploy 当前工具层没有强制校验前缀,这一步靠 agent 自觉。

## 2. 设计规范

| 条文 | 内容 | 备注 |
|---|---|---|
| 平级扩展禁令 | **不允许对一个业务对象(或单据转换)做多个平级扩展**;多安装包 / 多行业产品导致的平行扩展,必须显式指定加载顺序 | OpenDeploy 的"单层树规则"硬约束已对齐——每个父对象顶多挂 1 个本项目扩展,工具层直接拒绝第二个并列扩展 |
| 字段数上限 | 一个单据的字段总数原则上 ≤50(含隐藏字段) | 工具层未强制;agent 做大方案(一次加十几个字段)时应自查提醒 |
| 停靠布局 | 上下左右停靠元素各 ≤1 个,中间停靠 =1 个;停靠元素的同级不允许存在绝对布局元素 | 手工设计器操作场景,OpenDeploy 当前不生成布局 |
| 默认属性按需 | 单据列表默认显示、支持引出、支持引入等按业务需要设置 | OpenDeploy 加字段时的默认值要跟需求核对,不要全开 |
| **网控必须配置** | 防止并发修改数据导致数据错误 | 单据并发修改场景,agent 出方案时若涉及多人编辑的单据要提醒 |
| 基础资料主键 | 建议整型,否则不支持单据转换 | 建基础资料对象时的选型约束 |

## 3. 典型误判

1. **"字段标识就是给人看的,随便起"**——错。标识会进元数据、进转换规则映射、进插件代码引用;乱起名在多 ISV 环境会冲突,且官方条文明确要求 ISV 前缀。
2. **"同一个单据我再开一个扩展改点别的,互不干扰"**——违规。平级扩展加载顺序不显式声明时行为不可预测;正确做法是都堆到同一个扩展里(OpenDeploy 已强制),或走显式的平行扩展顺序设置。
3. **"50 个字段是软建议,我先加 80 个再说"**——原则上不允许。字段数膨胀直接影响列表性能和单据打开速度;真需要那么多,先评估拆子单据体 / 关联对象。

## agent 话术模板

> 按金蝶二开规范,新加的元素我用项目的开发商代码前缀命名:字段标识 `PAAB_CreditLevel`、物理字段 `F_PAAB_CreditLevel`。这样在客户环境跟其他 ISV / 标准产品不会冲突,以后打补丁过质量门禁也不卡命名这一关。
