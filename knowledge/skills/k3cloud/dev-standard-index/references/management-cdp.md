# 定制开发管理规范 + API 开发规范 🟡

> 管的是"人、平台、过程、质量、环境"——部署上线 / 流程合规类问题看这个文件。

---

## 1. 岗位配置与职责

| 岗位 | 职责 | 对质量负责的部分 |
|---|---|---|
| 实施顾问 | 需求制定、需求验证、回归测试、部署上线 | 需求的合理性、项目质量 |
| 软件开发工程师 | 设计开发、单元测试、功能测试、缺陷修复 | 设计合理性、开发质量 |

**OpenDeploy 视角**:OpenDeploy 的用户就是"实施顾问"这一栏——所以 agent 生成方案时要意识到:用户可能同时扮演两个角色(一人交付团队),规范里归工程师的活(单元测试、代码质量)agent 要主动兜住,不能只管"把东西配出来"。

## 2. 开发平台使用(硬性要求)

1. **项目研发过程必须使用星空协同开发云 + 项目协作系统**(DevOps)——需求 / 任务 / 缺陷都在项目协作系统里流程化,保留各节点文档。
2. **在协同开发云建立开发应用**,应用名称与客户正式名称一致;所有干系人(实施 / 开发 / 伙伴开发者 / 客户 IT)以参与者方式加入应用协作开发。
3. 开发内容包含:业务对象、插件、配置文件、第三方组件、自定义客户端。
4. **特殊客户定制要延用集成开发平台的,必须申请权限 + 明确告知风险,批准后才能开通**。

**OpenDeploy 视角(2026-08 判断)**:第 4 条说明官方已把"集成开发平台(数据中心直改)"从默认路径降级为例外审批路径。OpenDeploy 现有的 `SaveForIDEV9` 直改链路对应的就是这个"例外"场景:
- 未被协同应用锁定的私有云环境:直改模式继续可用,但要在话术里告知用户"规范层面这属于需申请延用的旧模式,改动不进版本管理"
- 已上协同开发云托管的环境:正确路线是"OpenDeploy 生成产物 → 用户在协同开发云应用里落地(引入业务对象 / 插件工程 / 签入 → 在线构建 → 部署)"
- 保存前如果探测到数据中心与协同应用双向锁定,必须告警,不能静默直改

## 3. 开发过程管理(五阶段)

需求分析(需求规格说明书 + 协作系统评审)→ 技术设计(详细设计 + 任务评审)→ 开发构建(业务对象开发在协同平台做,代码走应用源码服务,迭代完成 → **在线构建** → 修质量问题,安装包部署测试环境)→ 测试验证(SIT / UAT)→ 上线发布(PRO)。

**OpenDeploy 视角**:agent 做方案时,`implementation-planning` skill 的产出物可以对齐这五阶段的语言(需求澄清 → 设计 → 构建 → 验证 → 上线),让用户拿到的东西天然能贴进协作系统的节点文档。

## 4. 开发成果质量管理(质量门禁)

1. 开发完成后在协同开发平台**在线构建**,质量检测平台自动出质量报告。
2. 检测维度:**SQL 脚本、第三方资源、业务对象检查、插件代码扫描**。
3. **"严重"和"阻断"问题必须修复,最终质量得分 ≥70 分,安装包才能进入测试部署环节**。
4. 质量报告同时是公有云部署、生态产品上架应用市场的依据。

**OpenDeploy 视角**:这四条检测维度就是 agent 生成产物的自查清单——生成的 Python 插件 / C# 源码 / SQL 脚本要在源头避开会触发"严重 / 阻断"的写法,而不是等用户构建被打回。C# 禁用代码清单见 `code-and-script-rules.md`。

## 5. 开发工程管理

### 5a. 环境

建议四套:**DEV / SIT / UAT / PRO**,四套环境的**版本和补丁必须保持一致**;UAT 测试通过的补丁包才可正式部署 PRO。

### 5b. 代码托管

- 必须用协同开发云,源码统一走**应用源码服务**(SVN),可做迭代分支管理
- **定制开发源码不允许上传 GitHub 等开源代码托管平台**

### 5c. 构建与制品

- CI/CD 用协同开发云**在线构建**实现:业务对象 + 代码 + 预置数据一体化构建
- 构建产物 **kdpkg 包**在协同开发云制品库统一管理:可手动下载到本地安装 / 公有云客户推送安装 / ISV 推送到应用市场

**OpenDeploy 视角**:kdpkg 制品库是"OpenDeploy 产物进协同管道"的天然出口——未来如果做"导出为可导入产物"(元数据 / 预置数据),目标格式应该对齐在线构建的输入,而不是另造一种包。

## 6. API 开发规范(概要)

1. API 开发必须使用金蝶云星空**第三方系统登录授权**,由系统管理员确认授权,保障秘钥安全。
2. 已授权的第三方登录信息必须正确配置,**禁止未经授权分发给其他第三方**。
3. 必须使用**标准 SDK**(API 中心下载),按接口标准调用。

**OpenDeploy 视角**:集成类需求的落地方案看 `k3cloud/webapi-index`;这里的关键合规点是"授权由客户管理员操作、秘钥不扩散"——agent 帮用户配集成时,登录信息要落在客户自己的配置里,不要出现在会话产物 / 插件代码里。

## agent 话术模板

### 场景:用户问"我们这么改符不符合金蝶规范"

> 金蝶的《二次开发规范》在管理层面有三条硬要求:开发必须在协同开发云上做(集成开发平台要申请延用)、质量分 ≥70 才能部署、源码必须走它的 SVN 不能放外部托管。你说的这个改动本身【合规点 / 不合规点】……
